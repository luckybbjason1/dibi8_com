전형적인 실패는 오케스트레이터가 『인증 모듈을 리팩터링했고 모든 테스트가 통과한다』라는 보고를 읽고 그 단계를 완료로 표시한 뒤 다음으로 넘어가는 것이다 — 실제로는 서브에이전트가 타입 체크는 통과하지만 런타임에 깨지는 얕은 수정만 했고 테스트를 한 번도 실행하지 않았는데도 말이다. 항상 실제 근거에 대조해 검증하라: git diff, 테스트 종료 코드, 에이전트 A를 /auth/로, 에이전트 B를 /payments/로 겹침 없이 범위를 정하거나, 각자에게 워크트리를 줘서 독립된 체크아웃에서 작업하게 하라. 두 작성자가 하나의 작업 트리를 공유하게 절대 두지 마라.” q: “멀티 에이전트 실행 비용이 예상의 10배가 나왔다. 무슨 일이 있었나?” a: “폭주하는 팬아웃이다. 작업량이 정당화하는 것보다 훨씬 많은 에이전트를 띄웠거나, 수렴 조건 없는 루프 안에 에이전트 생성을 넣어 계속 돌게 한 것이다. 해결책은 예산과 정지 조건이다: 단계별 에이전트 수에 상한을 두고, 탐색 루프에는 『끝날 때까지 계속』 대신 『새로운 것이 없는 라운드가 K번 지나면 정지』 규칙을 쓰라. 모든 서브에이전트는 컨텍스트 하나치의 토큰을 잡아먹는다 — 반사적으로가 아니라 의도적으로 팬아웃하라.” q: “왜 파이프라인은 성공을 보고했는데 뻔한 발견을 놓쳤나?” a: “조용한 절단이다. 탐색 에이전트가 결과를 상위 N개로 잘랐거나, 전체를 훑는 대신 표본만 봤는데도 작업이 누락됐다는 것을 아무도 로그에 남기지 않은 것이다. 그러면 오케스트레이터는 실제로는 표면의 60%만 감사했는데도 『감사 완료』라고 보고한다. 해결책은 절단을 시끄럽게 만드는 것이다: 에이전트가 자기 커버리지를 제한했다면 보고에 반드시 그것을 밝혀야 하고, 오케스트레이터는 부분 결과를 완료인 양 조용히 제시하는 대신 『검사하지 않은 항목 N개』를 드러내야 한다.” q: “에이전트 파이프라인에서 git 워크트리는 무엇이 잘못되나?” a: “방치된 워크트리와 누출된 상태다. 워크트리 격리를 받은 서브에이전트가 변경을 하고 오케스트레이터가 결과를 읽지만 아무도 정리하지 않는다 — 그래서 낡은 워크트리가 쌓이고, 더 나쁘게는 나중의 에이전트가 절반만 끝난 워크트리를 메인 트리로 착각해서 읽는다. 해결책: 워크트리를 범위가 정해진 자원으로 다뤄라. 변경이 없으면 자동 정리하고, 변경이 있으면 명시적으로 검토 후 병합하거나 폐기하며, 하류 에이전트가 다른 에이전트의 워크트리를 정본 상태인 양 절대 읽지 못하게 하라.” q: “이렇게 자주 실패하는데도 멀티 에이전트 오케스트레이션은 복잡성을 감수할 가치가 있나?” a: “있다. 작업이 진짜로 컨텍스트 윈도우 하나를 넘어서거나 독립적 검증이 필요할 때라면 — 하지만 이 다섯 가지 실패야말로 반사적으로 손대지 말아야 할 이유다. 잘 프롬프트된 단일 에이전트는 버그투성이 5-에이전트
